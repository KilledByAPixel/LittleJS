# LittleJS Project - AI Agent Instructions

These instructions are for making changes in the LittleJS repo safely. Optimize for small diffs, clarity, and ease of use.

## Non-negotiable rules

- **Prefer minimal, local changes.** Do not refactor for style unless asked.
- **No new runtime dependencies.** Keep LittleJS dependency-free at runtime.
- **Do not hand-edit generated build artifacts.**
  - Treat `dist/` as generated output.
  - Make changes in `src/` (and `plugins/` when appropriate), then run the build.
  - **`dist/` is committed only for a release.** Build it to run the tests and the examples, and leave it out of the commit (`git add -A -- . ':(exclude)dist'`), so between releases it shows as modified in the working copy. The repo's `dist/` is the last release; a rebuild may be committed between releases with a patch version bump when there is a reason to. The live site does not use the committed one: [.github/workflows/pages.yml](.github/workflows/pages.yml) builds `dist/` from the source on every push to main and deploys the repo with it.
- **Match surrounding style.** Follow the conventions in the files you touch.
- **Avoid breaking public APIs.** If a change could break users, call it out clearly and offer a compatible alternative.
- **Keep agent-generated working files under `.claude/`.** `docs/` is the published JSDoc API site and is fully generated — never hand-edit it, and don't regenerate it unless asked (see Documentation below). Superpowers plans go in `.claude/superpowers/plans/` and specs in `.claude/superpowers/specs/` (overrides the skill defaults). The `.claude/` folder is gitignored.

If anything in this doc conflicts with the actual repo behavior, follow the repo behavior and update this doc.

## Architecture overview

LittleJS is a modular HTML5 game engine with:

- **Core engine**: `src/engine*.js` (main loop, objects, rendering, physics, input, etc.)
- **Plugins**: `plugins/*.js` (optional features like Box2D, post-processing, UI, audio helpers, etc.)
- **3D**: `plugins/math3d.js` (Vector3, Matrix4, Ray3D, 3D collision and raycasts) and `plugins/render3d.js` (the 3D renderer: the plugin, the camera, the shaders, shadows and the draw pass) with `plugins/render3dMesh.js` (Mesh, its packing for the GPU and the basic builders) and `plugins/render3dObject.js` (EngineObject3D and its collision, InstancedMesh3D, Light3D and DirectionalLight3D) after it, then `plugins/render3dExtras.js` (the other builders, HeightMap, camera controls, particles, trails, the OBJ loader, CSG: things built on the renderer that it does not need to draw), `plugins/gltf.js` loads glTF and GLB models onto it, `plugins/render3dVoxels.js` has VoxelMap, `plugins/render3dLevel.js` loads 3D levels, and `plugins/render3dDebug.js` has the 3D debug draws, debug only like the 2D ones and stubbed in `src/engineRelease.js`. `plugins/render3dEditor.js` has the free camera and the 3D level editor, debug only and stubbed the same way. All are plugins in the same bundle, and `plugins/threejs.js` is the alternative that renders with Three.js.
- **Parallax**: `plugins/parallax.js`, `ParallaxLayer`, a CanvasLayer that follows the camera by its `parallax` and repeats across the view (`getDrawPositions`), its image drawn once by a function, `parallaxMountains` by default, whose ridge ends where it starts (`parallaxRidge`) so it tiles; the Parallax short and the platformer use it, [test/browser/parallax.html](test/browser/parallax.html) checks it on pixels
- **Tile sets**: `loadTiles` (plugins/textureSheet.js) packs tile images onto the texture sheets through the sheet queue, in the order given, and hands back a TileInfo whose `tiles` list fills in as they load; a TileLayer keeps that list on its own tileInfo, and the tile layer's draw, `editorTileInfo` and the editor's palette read tile n from `tiles[n]` before the grid; [test/tileSet.test.mjs](test/tileSet.test.mjs), and [test/browser/layers2d.html](test/browser/layers2d.html) on pixels
- **Level files**: `tileLayersLoad` reads Tiled JSON, with the first tileset's `margin` and `spacing` when it is kept in the map (a TileInfo at the margin, padded by half the spacing, with the tileset's own columns), and `tileLayersFromLDtk` makes an LDtk level a Tiled map, so the loaders and the editor have one format: an IntGrid layer is a hidden layer of its values under its own name, the collision layer a game names (`collisionLayer` takes a name), since stacked and see-through tiles add layers and move the indices; [test/ldtk.test.mjs](test/ldtk.test.mjs)
- **Level editor**: `src/engineEditor.js`, debug only; object layers (`objectLayersAddType`, `objectLayersLoad`) ship in `src/engineTileLayer.js`. See "Level editor" below
- **Build system**: `src/engineBuild.mjs` (concatenates modules into distributable bundles)

## Repo structure and file types

### Engine source (`src/*.js`)
- Modular architecture (one subsystem per file)
- Concatenated at build time (internal source does not use ES modules)
- Code is vanilla JavaScript with type info expressed via JSDoc comments

### Build output (`dist/`)
Common outputs include:
- `littlejs.js` - Full bundle (debug features included)
- `littlejs.release.js` - Production bundle (debug stripped)
- `littlejs.esm.js` - ES module build (import/export)
- `littlejs.esm.min.js` - Minified ES module
- `littlejs.d.ts` - TypeScript definitions

Use via script tag or ES module import:
- `<script src="dist/littlejs.js"></script>`
- `import * as LJS from './dist/littlejs.esm.js'`

Prefer adding new optional features as plugins when it keeps the core simpler.

### Examples
- `examples/starter/` - Plain JavaScript global usage via `<script>` (recommended starting point)
- `examples/module/` - ES module import pattern
- `examples/typescript/` - TypeScript example usage
- `examples/shorts/*.js` - Single-file demos loaded by the shorts harness; the 3D ones are `render3d*.js`
- `examples/3d/` - The 3D plugin in one scene; `examples/threejs/` - the same idea rendered with Three.js

### Benchmarks (`bench/`)
- Pages that run LittleJS and other engines (three.js, PixiJS and Phaser, loaded from a CDN) through the same scenes, and `all.html` runs the whole set and prints a table to copy; `bench/README.md` says how to run them and how to read the numbers
- Per frame work in a LittleJS bench page goes in a pre render hook, not gameUpdate, since the fixed timestep runs gameUpdate several times a frame below 60 fps and would count it several times over
- The GPU time comes from a timer query and only means something when the frame is at the refresh rate; a CPU bound page shows its CPU time there

### Short examples (`examples/shorts/*.js`)
Short examples are special:
- Pure JS code file, no HTML
- No imports, do not use LJS namespace - engine APIs are available globally
- Override hooks: `gameInit()`, `gameUpdate()`, `gameUpdatePost()`, `gameRender()`, `gameRenderPost()`
- Lines stay within 80 columns, and colors are written with `hsl(...)`, never `rgb(...)`
- Each short is listed in `examples/shorts.js` with a name, a short description and search keywords
- The example browser sets `setTileDefaultPadding(1)` for every short, since `tiles.png` has a 1 pixel border around each tile, so a short does not set it; one copied into a project of its own needs that line
- A short ends with its write-up, a block comment whose first line is `/* info`, the last thing in the file and its only block comment: markdown (headings, paragraphs, one level lists, code, bold, italic, links) that the example browser takes off the code and shows in the info box under the code (`splitExampleInfo`, `renderExampleInfo` in `examples/shorts.js`), which Show Info hides. In a code span, each name the docs' index knows (`docs/search.js`, which the page loads) links to its docs entry, a name two classes share left plain, and from `## See also` on, an example's name links to that example and switches to it in place, so See also names examples exactly as `examples/shorts.js` lists them. The box sits under a handle that drags to share the column's height with the code, kept in the page's saved preferences, and on a phone the list is a full screen picker: a short with no block shows its description from the list, and a full example, which is a folder, has its write-up in `fullExampleInfo` in `examples/shorts.js`. It says what the example shows, then `## How it works`, `## Try it` and `## See also`, as `helloWorld.js` and `pongGame.js` do; what a short is about goes there and not in a comment at its top, and the text can not contain `*/`. Every engine name it mentions is checked in the source, and every Try it edit is run. [test/docs.r5.test.mjs](test/docs.r5.test.mjs) checks the form, [test/exampleBrowser.test.mjs](test/exampleBrowser.test.mjs) the split and the markdown

## Coding conventions

### Factory functions vs constructors
Prefer factory functions for core types:
- `vec2(x, y)` not `new Vector2(x, y)`
- `rgb(r, g, b, a)` or `hsl(h, s, l, a)` not `new Color(...)`
- `tile(index, size)` for tile info

Use constructors for game objects and complex types:
- `new EngineObject(pos, size)`
- `new ParticleEmitter(...)`
- `new Sound(zzfxParams)`
- `new Timer(duration)`

### Naming
- `camelCase` for variables and functions
- `PascalCase` for classes
- `UPPER_CASE` for constants that are truly constant (like `PI`)

### Code style
- Use JSDoc with `@memberof` grouping (namespaces: Engine, Math, Draw, Input, Audio, Debug, Settings, etc.)
- Prefer single-line comments: `// comment`
- Use `ASSERT(condition, 'error message')` for validation (stripped in release)
- Use `LOG(...)` for debug output (stripped in release)

### Type checking
Use built-in type helpers for validation:
```javascript
isNumber(n)   // true if number and not NaN
isStringLike(s) // true if stringifiable (has toString returning a string)
isArray(a)    // true if array
isVector2(v)  // true if valid Vector2
isVector3(v)  // true if valid Vector3 (3D math plugin)
isColor(c)    // true if valid Color
```

A field that starts as `undefined` reaches `dist/littlejs.d.ts` as `any`, because tsc infers field types from their assignments. Give it a `@type` tag beside its `@property` tag, the way `fogColor` and `obj.shader` do:
```javascript
/** @property {Shader|undefined} - Custom shader to render with
 *  @type {Shader|undefined} */
this.shader = undefined;
```

### Math aliases
Engine source exposes short aliases for common `Math.*` calls — prefer them
over `Math.X` in engine and plugin code:
```javascript
abs, floor, ceil, round, min, max, sign, hypot, log2, sin, cos, tan, atan2, PI
```
For things without an alias (e.g. `Math.trunc`, `Math.SQRT2`), use `Math.*` as normal.

### 3D plugin conventions
The 3D API mirrors the 2D one, so the same rules hold unless a 3D reason overrides them:
- Argument order follows 2D: `tileInfo` before `color`, and `EngineObject3D(pos3D, mesh, tileInfo, color)` like `EngineObject(pos, size, tileInfo, angle, color)`
- Builders, draws and objects take full sizes (diameters), like `drawCircle`; the math helpers (`collideSphereBox`, `raycastSphere`) and `Light3D` take a radius, and the parameter says which
- The `3D` suffix goes on fields that have a 2D counterpart (`pos3D`, `size3D`, `velocity3D`), on classes with a 2D namesake (`Camera3D`, `Light3D`, `ParticleEmitter3D`) and on functions where nothing in the name says 3D (`isOverlapping3D`, `collideBoxBox3D`); `Mesh`, `HeightMap` and `raycastSphere` need none
- Meshes come in two forms. The builders make triangle strips: every strip repeats its first point, the odd triangles read the other way, and the pass draws with `frontFace(CW)`. `addTriangles` and the model loaders make indexed lists, `mesh.indices` over vertices held once, listed counter clockwise from the front like a strip's first triangle. On upload, `mesh.getTriangles()` gives the GPU an indexed list either way, turning a strip into its real triangles so the joins cost nothing, and `bufferCount` counts indices. `toIndexed()` turns a strip mesh into the list form, which combine and addStrip do on their own when the forms meet. A `dynamicDraw` mesh keeps that layout, so a dirty upload only rewrites the vertex values. A builder that knows which strip entries are one vertex sets `mesh.vertexKeys`, and the upload skips the search; `buildGrid` does for a smooth grid. Back faces are culled unless `mesh.doubleSided` is set, which the open builders (`buildGrid`, `buildRibbon`, an uncapped lathe) do themselves
- Mesh operations return a new mesh and never change their inputs, since builder meshes like `render3D.boxMesh` are shared: `mirror`, `spin`, and CSG (`union`, `subtract`, `intersect`). The builders' bevels are parameters, 1 segment a chamfer. CSG is a port of csg.js's BSP trees in render3dExtras.js, walked with loops so a deep tree cannot overflow the stack. The trees only tell inside from outside: the polygons stay in lists, and a polygon is cut at the other mesh's box so only the part inside it is clipped, which keeps repeated cuts from multiplying triangles. The weld after it merges points within the 1e-5 epsilon only, since moving a point farther takes it off its plane and the next cut splits it again. The assert that CSG input is closed sums the triangles' area vectors, so slivers a few epsilons wide left by earlier cuts pass. Parts that overlap must be joined with `union`, not `combine`
- Draw state lives on `render3D` (`additive`, `emissive`, `specular`, `receiveShadow`, `shader`, ...), listed in `RENDER3D_STATE_FIELDS` and written out by hand in `render3DCaptureBatchState`, `render3DApplyBatchState` and `render3DStateChanged`, which are the batch key: a change flushes the pending batch, and a new field goes in all four, in `render3D.drawState` and the `Render3DDrawState` typedef, and gets an accessor. Each field is an accessor over `drawState` whose setter moves `render3D.stateVersion` only on a real change, so the batch check at every draw is one number while the state holds; code on the per draw path must not set a field and set it back (drawMesh's batch keys on its matrix's mirroring itself instead of setting `mirrored`), or every draw pays the full compare. The stage loop sets it from each object's flags through `render3DSetObjectState` and resets it before every callback, so an object's flag is never read at draw time by anything else
- Level collision in 3D: `HeightMap` and `VoxelMap` are EngineObject3D that draw themselves and join `render3DLevel` when made, and leave it on destroy. An object with `collideLevel` (on by default in 3D `setCollision`) and a mass is resolved against them in updatePhysics, through each one's `levelCollide3D(o, oldPos, wasOn)`, which sets `groundObject` (wasOn says it stood on that one last frame, so a HeightMap keeps it on a slope going down); a solid sets it too, when its push is within the standing object's `groundAngle` of straight up, and that push is turned straight up so nothing creeps down a ramp. Solid boxes turn with `rotation3D` (the math3d box helpers take an optional rotation, turned boxes meet by the separating axis test), while level collision still takes an object as its upright box. `damping`, `angleDamping`, `clampSpeed` and `friction` act in 3D as in 2D; `render3D.pick` hits their surfaces through `levelRaycast3D`. VoxelMap's pos3D is its corner and a cell is one unit; HeightMap's pos3D is its center. Both stay upright and unscaled. A test that makes a HeightMap as a plain lookup destroys it, or it catches the bodies of the tests after it
- Billboards: an opaque one (`drawBillboard`, or a sprite object, with no blend) is one more instance of `render3D.billboardMesh`, batched like a mesh's uses and drawn at the stage's end, its see through texels dropped by the shader; one that blends is written into the stream in its sorted place. Both are unlit on screen by a flag on the batch (`instanceUnlit`, `streamUnlit`, given to `render3DInstanceSlot` and `render3DBeginStrip`), never by setting `lighting` and setting it back. [test/billboardInstancing.test.mjs](test/billboardInstancing.test.mjs)
- Picking: `render3D.pick`, `engineObjectsRaycast3D` and the editor go through `render3DRaycastObject`, which hits a mesh on its triangles (`render3DRaycastMesh`, in the mesh's own space, after its sphere and its box as quick rejects): only the faces the pass draws, so a mesh seen from inside is not hit unless it is `doubleSided`, as three.js does. It walks the strip or the index list as it is and keeps nothing, so a changed mesh needs no invalidation. A sprite is its quad, a mesh flattened to nothing a disc, a ray of no length is where it starts in the box, and an InstancedMesh3D is never hit. [test/pickTriangles.test.mjs](test/pickTriangles.test.mjs)
- An `EngineObject3D` keeps its world matrix and rebuilds it only when its position, rotation, scale or its parent's matrix changed; plugin code reads it through `render3DObjectMatrix(o)` and never changes it, and `getMatrix()` hands out a copy
- 3D draws only work inside the 3D pass (an object's `render3D()` or `render3D.onRenderOpaque` / `onRenderTransparent`); asserts belong outside the pass, since the pass has a try/finally that hands the GL state back to 2D
- Spotlights: a `Light3D` with a `coneAngle` shines along its own forward (`getForward3D`, -Z), fading over `coneSoftness` of the cone; the shader gets each light's cone as four numbers in `extraLightCones` (`render3DLightCone`), which are (0, 0, 0, -1) for no cone so the factor is exactly 1 and old scenes stay pixel-identical. `render3D.shadowLight` makes one spotlight the shadow caster (`render3DShadowCaster`): `updateShadowMatrix` builds a perspective map down its cone, `shadowParams.x` is 1 for the sun's shadow and 2 + the light's index for a spotlight's, and the bias is divided by `S.w` squared in the lookup, which is 1 for the sun's flat map and the distance for a spotlight's. One shadow caster at a time. Its `gel` is a texture on unit 4 (`gelTex`, bound for the pass, white when none, emptied with the material units), read in the shader's `gel()` at the fragment's place in the shadow map, turned into the light's own right and up by `render3D.gelAxes`, since the map's axes do not follow the light's turn and must not change, or old shadows would move; white makes a light with no gel pixel for pixel as before (`.claude/gel/identity.mjs` compares builds). [test/browser/spotLight.html](test/browser/spotLight.html) checks the cone, the shadow and the gel on pixels
- Lens flare: `LensFlare3D` (render3dExtras.js) is the sun's flare, an object that draws in the 2D pass, its `render()`, as additive screen space tiles over the 3D scene, on a texture of three shapes it draws itself (`render3DFlareTile`); its field for size is `flareSize`, since `size` is the 2D size every object has. `visible` eases toward whether the sun shows: in front of the camera and, with `occlusion`, not behind anything `render3D.pick` finds along the ray to the sun among the objects that are not see through. Its shapes are the six of `render3DFlareShapes`, the hexagon set pixel by pixel since a gradient is round, and an element may be a tile of the game's own (`tileInfo`). `light.addFlare()` on a Light3D makes one for it and returns it, and `light.flare` is that flare or undefined, an accessor that sets `flare.light` and makes the flare the light's child, so it stays or goes with the light through a scene change (it takes no true or false: tsc gives a JS setter its getter's type, so a property that took a switch and gave back an object could not be typed), and the level's Light has a `lensFlare` property, not `flare`, since the loader also sets a property on the object. `flareLook` is how the flare would show with nothing in the way, undefined when it would not at all, and `update` only sends its ray then, so flares off the screen cost nothing. With `flare.light` set it is that Light3D's flare in place of the sun's (`flareSource`), far away like the sun's for a directional light: at the light, in its color, smaller from farther than its radius, hidden only by what is nearer than the light and not by the lamp the light is inside (a mesh whose box holds it, whose surface the ray hits within near = min(2, radius * .4) of it, and whose thinnest scaled side is at most 2 * near, since a room or a level mesh holds its lights too; four lamps are looked past, a fifth counts as hidden), and a spotlight's only from inside its cone. [test/browser/lensFlare.html](test/browser/lensFlare.html) checks it on pixels
- Lighting: `render3D.sunDirection` points toward the sun, a `DirectionalLight3D` shines from its position toward the origin, `emissive` is a number (0 lit, 1 its own color, above 1 overbright), and `rotation3D` is Euler pitch, yaw, roll applied roll, pitch, yaw. All of it matches three.js, and REFERENCE.md has a "Coming from three.js" section to keep in step
- Materials: `normalMap` (cotangent frame from `dFdx`/`dFdy`, no tangents, green up the image, read at the color texture's uvs), `shininess` (an object's `roughness` is an accessor over it, 2 / r^4 - 2, nothing kept of its own; glTF's roughnessFactor goes through it), `reflectivity` (Schlick toward the colors buildSky gave `render3D.sky`, kept in `render3DSkyColors`, or the ambient colors) and `emissiveMap` with `emissiveMapColor` are draw state like `specular`; the maps ride texture units 2 and 3, and a spotlight's gel unit 4, white when unused, set by `render3DSetMapUnits` at the pass start and emptied at its end. Each part of the shader is off by default, so a scene that sets none draws pixel for pixel as before; `.claude/materials/check.mjs` (not in the repo) checks that against the old build in headless Chrome and Firefox
- Environment maps: a `CubeMap` (`makeCubeMap`, `loadCubeMap`) uploads once per context (`render3DCubeTexture`, faces in GL's order and orientation, `render3DCubeDirection`) with mipmaps. GL's cube is left handed, so `loadCubeMap` draws each image mirrored and swaps +x and -x, which shows a sky box set as three.js does (it samples at -x instead); `makeCubeMap` and capture go by direction and need nothing. `render3D.environment` rides unit 5, bound by `render3DSetMapUnits`, and with it set a reflection reads it in place of the sky gradient, at a mip level from shininess, blurred over half the angle of the highlight's spread, so a map of any size blurs the same (`envParams.z` is log2(size * .45)), or from how far the reflection turns between pixels when that is more (`envParams.w`, `dFdx(q)`), so a small mirror does not sparkle; the blur stops at a 4 by 4 face (`envParams.y`), since mipmaps blur each face alone and a smaller one only shows its faces' seams. `render3D.skyBox` is drawn by `render3DDrawSkyBox` on unit 6 as one triangle over the screen, with a program of its own, in place of the dome. An object's `environment` is the draw state field `environmentMap`, bound to unit 5 per draw when it changes (`render3DBindEnvironment`). A `CubeMap` made with no faces is drawn from the scene: `capture(pos3D)` adds it to `render3D.cubeCaptures`, and the default pass draws it after the shadow map (`render3DCaptureCubes`), each face through `render3DCubeFaceMatrix`, the camera swapped for one whose matrix is the face's; while it is drawn it is `render3D.capturingCube`, unbound from unit 5, not drawn as the sky box and not reflected, since a texture read while it is drawn is a feedback loop, and the debug draws stay out of it. [test/browser/environment.html](test/browser/environment.html) checks the faces and the blur on pixels
- Custom shaders: `Shader` (core, `src/engineDraw.js`) holds a `mainImage` snippet in the post-process style; each renderer wraps it with its own program on the first draw (`glShaderProgram` in 2D, `render3DFragmentSource` and `render3DShaderProgram` in 3D). The 3D fragment source is one function for the plugin's own program and every snippet's, so they cannot drift, and the promised snippet names are macros in `RENDER3D_SNIPPET_NAMES`. With no Shader set, rendering must stay pixel-identical

### Level editor
The editor paints a game's tile layers and edits its object layers while the game is paused, saving Tiled JSON:
- **Where it lives.** `src/engineEditor.js`, in the `engineDebugFiles` build list with `plugins/tweakables.js`, so the debug bundle has it and the release bundles do not; `src/engineRelease.js` stubs every name core code calls. Core has only small hooks: `tileLayersLoad` calls `editorMapRestore` and `editorMapLoaded`, `objectLayersLoad` calls `editorMapRestore` and `editorObjectMade`, `fetchJSON` calls `editorJSONFetched`, and `enginePreRender` calls `editorPreRender` so WebGL takes the editor's camera
- **The map is the source of truth.** The editor changes the Tiled map object the game passed to `tileLayersLoad` in place, and mirrors each change onto what the game made from it; saves and autosaves come from the map, never from the live layers, so tiles changed in play and the game's own post-processing never leak into a save. A game that loads the same map object again, as a restart does, gets the edits
- **Records.** `editorMapList` has a record for each map: `{map, layers, objectLayers, original, originalObjects, originalSize, key, hash, pending}`. A tile layer record is `{record, source, live, color}` (the Tiled layer and its live `TileLayer`); an object layer record is `{record, isObjects, group, name, instances}` (the Tiled object layer, undefined until the first object is placed, and what the game made for each object id). A layer the game built in code gets a map of its own. A map of objects alone, loaded with `objectLayersLoad` and no tile layer, is listed too and drawn from the map's size; the panel acts on `editorRecord()`, the selected object layer's or tile layer's map, and such a map steps aside when another map loads and none of its game objects are left
- **Every edit goes through one path, so undo, autosave and the game stay in line.** A tile: `editorPaint(layer, cell, gid)`. Objects: `editorChangeObjects(layer, (list)=> ...)`, which edits a copy of the layer's object list and has `editorSetObjects` bring the game's objects in line. Both add to the current stroke, and `editorStrokeEnd()` makes it one undo and autosaves it, or `editorStrokeCancel()` takes it back with no undo, as a selection drag does while it moves; a big edit (fill, clear, undo) runs inside `editorBulkEdit` so each layer redraws once. A resize changes the whole map, so `editorResize` makes it an undo entry of its own, `{resize, before, after}`, and the game makes its layers again through `onRestart`, without which a level can not be resized
- **Input.** Letter shortcuts are in `editorKeys` and `editorCtrlKeys`, read by the key's printed letter (`e.key`) from the editor's own listener; an action that returns `false` did nothing and leaves the key to the browser. Digits, Space and the mouse come through the engine's input in `editorUpdate`, which hands an object layer to `editorUpdateObjects`. In an editing session Escape (the debug key) switches between playing and editing
- **Adding a tool or key:** add it to `editorKeys` (and a button in `editorPanelInit` when it needs one), make the edit through `editorPaint` or `editorChangeObjects`, end with `editorStrokeEnd()`, and add it to `editorHelpLines` and, when it depends on what is held, `editorHint`
- **Adding an object property type:** `editorPropertyEditable` and `editorPropertiesUpdate` make its input, `editorObjectSetProperty` writes it as a Tiled property, and `objectLayersProperties` reads it back when objects are made
- **Game hooks.** `levelEditor`, an instance of `LevelEditor`, is the public API of both editors, and a game makes it its own through it (see EDITOR.md): the hooks (`onTile`, `onRestart`, `onPlayFrom`) and the moments (`onOpen`, `onClose`, `onUpdate`, `onDraw`, `onPanel`, `onSave`) are empty methods of the class, set on the instance or overridden by a class of the game's own given to `setLevelEditor`; a hook counts as given when it is not the class's own empty one, `editorHas(name)`, never by reading it. `addKey`, `addButton` and `addTool` keep what the game added on the instance (`keys`, `buttons`, `tools`) and each editor reads them from there: the game's keys before its own table, its box of the panel (`editorGamePanel`), its tool's press, drag and release in place of the editor's mouse handling (`editorToolUpdate`, `editor3DToolUpdate`), ended as one stroke. `edit2D` (`editorEdit2D`) and `edit3D` (`editor3DEdit`) are the edit functions a game calls. The 3D editor is the core's `editorOther`, which is how the class opens it and reaches its keys and edit functions with no core code naming the plugin. `src/engineRelease.js` has the same class doing nothing, so a game needs no guards. [test/editorExtend.test.mjs](test/editorExtend.test.mjs); `objectLayersAddType(name, make, defaults, tileInfo)` names the object types, with a string since minified builds rename classes. `examples/platformer` sets all of them
- **Save and autosave.** Save writes the map as Tiled JSON with everything it was loaded with, to a file picked once where the browser allows (Chrome, Edge), remembered across reloads in IndexedDB (`editorFileStore`), or as a download. A file Save wrote becomes the record's baseline (`editorSetBaseline`), for Reset to file; a download does not, it can not say it replaced the file, and neither does a file of another name, a copy, since the game still loads the one it came from. The browser gives a picked file's name and not its folder, so a file of the same name may be a copy too: after a Save the autosave stays, with `hash` (the file the game loads) and `savedHash` (the file written), and a reload that finds the file already has the edits drops it, while one of either file brings them back. The 3D editor does the same. Autosaves live in `localStorage` under `LittleJS editor <page path>`, one entry per map keyed by the file it was fetched from, or by its size, layer names and hash: `{hash, width, height, layers, objects, nextobjectid}`, and a resized map is resized again before its tiles are copied in. The hash covers the file's tiles, objects and shape (`editorMapLayout`: size, tile size, layers by id and name), and a file that changed under an autosave waits for Apply or Drop in the panel; Apply first checks the edits fit (`editorPendingFits`), and edits that do not stay waiting with their autosave, which is never dropped but by Drop
- **Tests.** `test/editor.test.mjs` (tiles, controls, autosave), `test/editorObjects.test.mjs` and `test/objectLayers.test.mjs` run headless on `test/vmEngine.mjs`; headless mode skips `inputUpdatePost`, so their `step()` clears the pressed keys by hand, and the panel is never made. The panel and drawing are checked in headless Chrome on the platformer, with scripts under `.claude/editorcheck` (not in the repo): a whole mouse drag inside one slow SwiftShader frame reads as a click, so drags are paced, and screenshots wait for the layer redraw

### 3D level editor
The 3D editor places and moves a 3D level's objects while the game is paused, saving plain JSON:
- **Where it lives.** `plugins/render3dLevel.js` is a normal plugin with `level3DAddType`, `level3DAddMesh`, `level3DLoad` and the built-in Box, Sphere, Cylinder and Light; `plugins/render3dEditor.js` is in `engineDebugFiles` after `src/engineEditor.js`, with the free camera and the editor. `src/engineRelease.js` stubs what other files call: `editor3DCameraBegin`, `editor3DCameraEnd`, `editor3DLevelLoaded`, `editor3DObjectMade`, and the input capture's `inputCaptureHides` and `inputCaptureMouse`
- **The level is the source of truth.** The editor changes the level object the game gave `level3DLoad` in place, and brings what the game made in line: an object that only moved, turned or changed size is moved where it is, one whose type or properties changed is made again, since constructors take the properties. Opening the editor puts every object back where the level has it
- **Every edit goes through one path.** `editor3DChange((list)=> ...)` edits a copy of the object list, `editor3DStrokeEnd()` makes the changes since one undo and autosaves, `editor3DStrokeCancel()` takes them back. Undo keeps copies of the list, 100 at most
- **The view.** The free camera and the editor draw with `editor3DCamera`, swapped in by `editor3DCameraBegin` from `render3DPreRender` and out by `editor3DCameraEnd` from `render3DRender`, so the game's update always has its own camera. The editor picks and projects inside `editor3DWithView`
- **Input.** While either is on, `inputCapture(true)` makes the game read every key and mouse button as up and no mouse movement, and they read inside `inputCaptureRead`. Keys are read by position (`KeyW`) through the engine's input, in `editor3DKeys` and `editor3DCtrlKeys`
- **The file.** `{littlejs3D: 1, objects: [{id, type, pos, rotation, scale, properties}]}`: rotation in degrees, a Color a hex string, a vector an array, and rotation, scale and any property left out when it is the default. `scale` multiplies the scale an object was made with, and collision follows `scale3D`
- **The scene block.** A level may have `scene: {sky, ambient, sunDirection, sunColor, fog, fogColor, shadows, lensFlare, skyBox, environment}`, applied by `level3DSceneApply` in `level3DLoad`; `skyBox` and `environment` are six image urls each, loaded in the background by `level3DSceneCubeMap` (the same urls once, `level3DSceneCubeMaps`), and a load is dropped when a newer scene or `editor3DSceneRestore` moved `level3DSceneCubeLoads` on before it finished; `lensFlare` is the sun's flare, an object and not a renderer setting, so `level3DSceneFlare` makes one only when the sun has none and takes away only the one a scene made, which is how `editor3DSceneRestore` puts it back: a key left out or wrong stays as the game set it, and no physics settings go here (gravity is the game's). The editor edits it through `editor3DChangeScene((scene)=> newScene)`, in the same stroke, undo entry (`sceneBefore`, `sceneAfter`), autosave, hash (`editor3DContentHash`), Reset and Save as the objects; `editor3DSetScene` first puts back `record.sceneBase`, the renderer as the game set it before the level's block, then applies the block, so a setting taken out shows the game's again. The Scene box is not made again while it has the focus, so its inputs change the scene as it is when they are used (`change(name, (now)=> ...)`), never from values kept when the box was made, or a field edited right after another puts the other back; [test/browser/editorScene.html](test/browser/editorScene.html) checks it. The scene, the blocks and the terrain are the level's parts, `editor3DLevelPartNames`, kept through one path: `editor3DChangePart(name, change)`, `editor3DSetPart`, a stroke's `parts` and an undo entry's `partsBefore` and `partsAfter`; a new kind of level content is a new name there and a branch in `editor3DSetPart` that shows it. `editor3DLevelParts` hands out shared copies (`editor3DPartCopies`), one per part until it changes, so undo steps do not each hold a terrain: copy one again before changing it or making it a level's own
- **The block map.** A level may have `voxels: {pos, size, blocks}`, its corner, its cells and its blocks as runs of a count and a type along x, then y, then z (`level3DVoxelsEncode`, `level3DVoxelsDecode`); `level3DLoad` makes it a `VoxelMap`, kept in `level3DVoxelMap`, with the sheet and setup of `level3DVoxelSetup`. The editor writes a level's runs in its own form when it takes the level, so the same map always compares the same. Painting sets blocks in the game's map as it goes (`editor3DVoxelSet`, the stroke marked `painted`) and `editor3DStrokeEnd` writes them into the level (`editor3DVoxelStore`); undo and the rest go by the level's block, `editor3DVoxelShow` bringing the game's map in line. The Blocks tool (B) is `editor3DVoxelPress` and `editor3DVoxelDragTo`: a drag stays on the layer of its press, by the plane of the face pressed, and `editor3DVoxelTarget` says which cell a ray is for and which way the face looks (`side`). With box fill on (X, `editor3DBlockBox`) the drag carries `start`, `grow`, `height` and `changed`, and `editor3DVoxelBoxTo` puts back what the drag changed so far and fills the box from its start to the mouse again, so a box dragged smaller takes blocks back; `editor3DVoxelResize` changes the map's size about its middle as one undo, its blocks staying where they are in the world
- **The terrain.** A level may have `terrain: {pos, size, height, color, heights}`, its center, its size in the world, how tall a full height is, and rows of 0 to 1; `level3DLoad` makes it a `HeightMap`, kept in `level3DTerrainMap`, at most 129 samples a side (`LEVEL3D_TERRAIN_SAMPLES`). The Terrain tool (T) sculpts the game's map in place while the mouse is held (`editor3DTerrainSculpt(point, mode, seconds)`, the stroke marked `sculpted`), rebuilding its whole mesh each time, which is what keeps the cap at 128 cells: about 21 ms a rebuild there and 106 ms at 256; raising it needs a rebuild of only what the brush touched. `editor3DStrokeEnd` writes the heights into the level to a thousandth (`editor3DTerrainStore`), and `editor3DTerrainShow` brings the game's map in line. The tool has three brushes, `editor3DTerrainBrush.mode`, X goes to the next: sculpt, flatten (toward the height pressed, the drag's `level`) and paint. Paint is `terrain.paint: {colors, cells}`, a list of colors and runs of a count and a color along the rows, 0 the terrain's own color (`level3DTerrainPaint`, `level3DTerrainSetColors`, which gives the HeightMap its vertex colors); while a stroke paints, the map's paint is in `editor3DTerrainPaints`, ahead of the level, and the store writes it with the colors no longer used left out
- **Handles.** `editor3DHandles()` lists them in world space, sized to stay the same on screen. Move follows the world axes, or with own axes on (L, `editor3DLocalAxes`) the object's own, where a drag goes in steps from where it started since the grid is the world's; Scale follows the object's own, and the three rings are pitch, yaw and roll, each changing one number of the rotation, and a ring seen edge on can not be taken. Snapping goes by the low corner of an object's box, so faces land on grid lines
- **Body drags and landing.** A drag of an object's body moves it level at its height, so it stays under the mouse, or across the view when seen from the side. With ground snap it then lands on what is under it (`editor3DLand`), climbing a step as tall as itself; a placed or pasted object lands the same way. What the game attached to an object, its children, counts as the object: a click on a part selects it, and it does not land on its own parts
- **Levels.** Each level has a record with its own undo and redo lists and its autosave key: the file it was fetched from, or for a level made in code `level #` and the hash of its objects as loaded. The loader reads a value of the wrong type as the default, does not set a property the type has no default for, and in debug builds skips an object its type can not make, with an error
- **Types.** A class is made with `new make(pos3D, properties)`, so it needs a constructor of its own that takes the position: one that hands every argument on to `EngineObject3D` would hand it the properties as its mesh. Any change to an object's properties makes it again
- **Prefabs.** A prefab is a small level, objects about its own origin: `level3DAddPrefab(name, {objects, attached})` makes it a type (`level3DPrefabs`, with `fromLevel` for one a level's own `prefabs` block added, which one the game added takes the place of), and its instance is a `Prefab3D`, a handle that makes its `parts` in `placeParts`, the first time it is placed: objects of their own in the world where `level3DPrefabPartTransform` puts them, since a child does not collide in 3D, or, attached, its children with their collision off, the handle then moved to the middle of the box around them (`originOffset`, `placeAt`), since an object's place is the middle of its body; the level keeps an instance by its prefab's origin, so the editor goes by `editor3DPos(object)` and never by an attached handle's `pos3D`. `level3DMakeAt` makes any object at a given place, `level3DSpawn` is that for a game. In the editor an instance is one thing: `editor3DParts` counts its parts, and its box is the box around them (`editor3DPrefabBox`), which is not about its place, so snapping, landing, dropping and pasting go by `editor3DBoxOffset`. `prefabs` is a level part; `editor3DPrefabsShow` brings the types in line and makes every instance again. `editor3DMakePrefab` (Ctrl+G) and `editor3DUnpack` (Ctrl+Shift+G) go between a selection and an instance. Edit prefab (Enter, `editor3DPrefabEnter`, `editor3DPrefabBack`, `editor3DPrefabStack`) loads a prefab as a level of its own, with no autosave (`editor3DPrefabLevels`), after destroying what the level had in the world; Back makes the prefab what was edited, at once in the registry, and once back in the level itself writes its own edited prefabs into it as one undo (`editor3DPrefabEdits`); a prefab of the game's own is changed in the registry and waits in `editor3DPrefabDirty` for Save inside it, which downloads its file. Closing the editor steps all the way out. Inside a prefab Make prefab and Attached are refused, and the autosave written is the level's, as it would be on going back (`editor3DAutosave` with the open prefabs merged into its `prefabs`). A registry entry keeps its `source`, the object it was added from: a prefab made of the level being edited, or one that holds it, is not in the Place list (`editor3DPrefabSelf`, `editor3DPlaceNames`). [test/level3DPrefab.test.mjs](test/level3DPrefab.test.mjs), [test/editor3DPrefab.test.mjs](test/editor3DPrefab.test.mjs)
- **Autosave.** Like the 2D editor's, a level whose autosave is over `EDITOR_AUTOSAVE_WAIT_SIZE` characters waits a second after the last edit (`editor3DAutosaveSoon`), and what waits is written by `editor3DAutosaveFlush` on close, a hidden page, another level loading and entering a prefab; inside a prefab it writes at once, since that autosave goes through the stack of open prefabs
- **Adding a tool or key:** add it to `editor3DKeys`, make the edit through `editor3DChange`, end with `editor3DStrokeEnd()`, and add it to `editor3DHelpLines` and `editor3DHint`
- **Tests.** `test/level3D.test.mjs`, `test/level3DScene.test.mjs`, `test/editor3DScene.test.mjs`, `test/level3DVoxels.test.mjs`, `test/editor3DVoxels.test.mjs`, `test/level3DTerrain.test.mjs`, `test/editor3DTerrain.test.mjs`, `test/inputCapture.test.mjs`, `test/editor3DCamera.test.mjs`, `test/editor3DMath.test.mjs`, `test/editor3DData.test.mjs`, `test/editor3DInput.test.mjs` and `test/editor3DPanel.test.mjs` run headless; the input tests set the mouse and keys the way the engine holds them and step. The panel and drawing are checked in headless Chrome on the 3D Level Editor short, with scripts under `.claude/editor3d` (not in the repo)

## Common pitfalls

- **New public APIs must be added to `src/engineExport.js`** - Variables and functions added to engine source files are accessible in script-tag builds automatically, but the ESM build (`littlejs.esm.js`) and TypeScript definitions (`littlejs.d.ts`) only include what's listed in `engineExport.js`. Plugin exports go in `plugins/pluginExport.js`. Forgetting this means ESM/TS users can't access the new API.
- **ASSERT and LOG are stripped in release builds** - Don't rely on side effects
- **Don't modify constant colors** - `WHITE`, `BLACK`, `RED`, etc. are frozen; use `.copy()` first
- **Time variables are global** - `time`, `frame` update automatically each frame
- **2D object collision goes through a grid above `engineCollideGridMin` solids** - `engineCollideGridWalk` hands a mover the solids near it in the list order checking every pair would, and finds them again when a push moves it; the grid follows each solid after its own updatePhysics and the other object after a collision callback. It must resolve exactly what every pair does, [test/collideGrid.test.mjs](test/collideGrid.test.mjs) runs a scene both ways and compares every value; a solid moved during physics by anything else, a callback moving a third object, is not followed until the next update
- **Fixed 60 FPS timestep** - Physics runs at 60 FPS regardless of display refresh rate. `setEngineVariableStep(true)` opts into one update per display frame with `timeDelta` the frame's time; per-frame values (velocity, gravity, damping, particle speeds) are not scaled, while values in seconds follow real time. Each frame's delta is first smoothed to whole display frames (`engineSmoothDelta`, after Frank's "Time Delta Smoothing"), from an internal frame estimate that is never exposed; deltas that do not fit whole frames of one length, like a variable refresh display, pass through as they are
- **A second finger is a pinch, not a second press** - with `touchPinchWheel` on (the default) two fingers turn `mouseWheel` by `touchPinch`, the mouse is between them and the button the first finger pressed lets go; a game with its own use for two fingers calls `setTouchPinchWheel(false)`
- **WebGL is enabled by default** - Set `glEnable = false` before `engineInit()` for Canvas2D only
- **Tile coordinates are bottom-left origin** - Y increases upward in world space
- **Every export must appear in REFERENCE.md** - [test/reference.test.mjs](test/reference.test.mjs) fails on a name that is exported but not mentioned, so a new API comes with its REFERENCE line
- **Files are stored with LF endings** - with `core.autocrlf` on, a working copy may be CRLF, so an edit script normalizes `\r\n` to `\n` before matching and writes LF back, or the whole file shows as changed
- **An instance divisor stays on a slot only while its array is enabled** - in Firefox, a plain draw that reads a constant attribute through a slot whose divisor is set makes the next instanced draw on that slot read garbage; Chrome does not care, so test the 3D plugin in Firefox too. `render3DDrawInstanced` sets the divisors with the arrays and clears both after
- **Canvas2D and WebGL line ends differ on purpose** - the main canvas strokes with round caps and joins (set in `engineUpdateCanvas`), which look better, suit text, and stop sharp corners spiking far out; WebGL outlines use square ends and mitered joins for speed. Don't "fix" either to match the other
- **A Shader on a 2D untextured draw does nothing** - `drawRect` carries its color in the additive slot with a zero tint, so the snippet's output multiplies away; draw a white tile instead
- **Engine and plugin draws pass screenSpace themselves** - the draw and debug functions default it to the game's `drawScreenSpace` setting, so a call in `src/` or `plugins/` that leaves it out would move to the screen when a game turns the setting on; pass `false` for world space; a new function or method with a screenSpace parameter defaults it to `drawScreenSpace`; [test/screenSpace.test.mjs](test/screenSpace.test.mjs) checks both

### Testing
```bash
npm test
```

- Most tests import `dist/littlejs.esm.js`; a test that needs engine internals or DOM events loads its own copy of the script build `dist/littlejs.js` through `loadEngine()` in [test/vmEngine.mjs](test/vmEngine.mjs), where `run(code)` can read internals and reassign engine functions like `drawTile`. Inside a `run(\`...\`)` template literal a regex backslash is lost, so write `[0-9]`, not `\d`. Rebuild with `npm run build` after changing source.
- [test/setup.mjs](test/setup.mjs) stubs minimal DOM and enables headless mode. Most tests shouldn't call `engineInit` or `render()`, or assume `time` advances — construct objects directly instead.
- To test time-driven logic (timers, cooldowns, spawns), call `setEngineManualStep(true)` before `engineInit`, then advance with `engineStep(frames)`. See [test/engineStep.test.mjs](test/engineStep.test.mjs). Call `engineInit` once per file at module scope: `frame` and `time` are module globals and monotonic, and `node --test` gives each test file its own process.
- Zero test dependencies — uses Node's built-in `node --test`. Match the style in [test/](test/) when adding new ones.
- [test/render3d.test.mjs](test/render3d.test.mjs) covers the 3D plugins headless: builder geometry and winding, draw state and batching decisions, collision and cameras. Nothing that needs a GPU (culling, lighting, a compiled shader) can be tested there; check that in headless Chrome with SwiftShader (`--use-angle=swiftshader --enable-unsafe-swiftshader`) through playwright-core, and never open a visible browser window. Firefox renders WebGL differently enough to matter, and its `--headless` mode runs pages without a window too, though its screenshot leaves the WebGL canvas out; have the page read its own pixels with `readPixels` and post them to a local server. Those harnesses live under `.claude/` and are not part of the repo.
- `npm run test:browser` is the browser smoke suite in [test/browser/](test/browser/): real WebGL in headless Chrome with the software renderer, no window and no dependency ([run.mjs](test/browser/run.mjs) drives the machine's Chrome over its DevTools socket with Node 22's WebSocket). Its pages read real pixels, one page a path: `draw2d` (rect, tile, additive), `layers2d` (a tile layer, 2D particles, a pixelated and a smooth texture), `parallax` (a parallax layer repeating and following the camera), `canvas2d` (the same draws with WebGL off, read from the main canvas), `lights2d` (the light system and its shadows), `shaders` (a 2D Shader and post process feedback), `focusBlur` (tilt shift, a postProcess value changed live, depth of field), `draw3d` (emissive, lit, instanced, the sun's shadow, a 3D Shader, a voxel block, a height map, an opaque sprite, 3D particles, 2D over 3D), `depth3d` (sceneDepth from the depth texture), `environment` (cube maps, the sky box, reflections and capture), `shaderFallback` (the plugins whose shaders fail, on the release build), `spotLight`, `lensFlare`, `editorScene` (the 3D editor's Scene box, its DOM only) and `contextLoss`; and every short runs 10 frames with no error or failed assert. A check that only says again what another says does not earn its place: a page has one check for each thing that can break on its own. `smokeSheet(...colors)` makes a sheet of plain tiles to hand `engineInit`. `npm run test:browser draw3d waterGame` runs only the pages or shorts named. A page writes `{checks: [{name, ok, detail}]}` into `<pre id=result>` through [smoke.js](test/browser/smoke.js), steps the engine by hand (`setEngineManualStep`), and reads the WebGL canvas right after a step. Without Chrome it skips, and fails where `CI` is set. The run is kept light on a machine someone is working at, and must stay so: one Chrome and 4 tabs at a time (more tabs are no faster, every tab draws through the one GPU process, and the software renderer takes every core of each Chrome started), at below normal priority, one run at a time by a lock file, stopped after 5 minutes, about a minute on a quiet machine. Never start a second Chrome or sweep the tab count to time it. A new short is covered once it is listed in `examples/shorts.js`.
- CI runs build + test + the browser smoke suite on every push/PR ([.github/workflows/test.yml](.github/workflows/test.yml)), on a build of the source, not the committed `dist/`.

### Documentation
```bash
npm run build-docs
```

- Generates the JSDoc site into `docs/` from `src/` and `plugins/`, with `README.md` as the homepage. Tooling lives in [tools/](tools/): `tools/docs/` is the site's own jsdoc template, `publish.js` the entry jsdoc calls and `render.js` the pure part that turns doclets into pages, tested by [test/docsTemplate.test.mjs](test/docsTemplate.test.mjs) on what jsdoc makes of `test/fixtures/docsFixture.js`. A symbol with no namespace in its `memberof` chain is internal and is not on the site; one whose owner is not a namespace or class (`Ease.LINEAR` under the constant `Ease`) goes under the nearest rendered owner with its dotted name; a class or typedef name documented twice fails the build, since types link by short name; a `@memberof` on a method, which names it `Class#method` under the namespace, is a build warning. An old `#.name` link is turned into `#name` on load. Source links go to the line on GitHub at the release tag. Namespaces are listed in the order `CORE_NAMESPACES` and `PLUGIN_NAMESPACES` give in render.js, a new one at the end of Plugins. A param whose type jsdoc rejects (a tuple) is read back from its tag, type, optional flag and description
- **This is not part of the normal workflow — do not run it after editing source.** It takes ~17s, rewrites ~100 files, and produces a large diff. The docs do not need to be current on every change. The repo owner asks for it when they want it.
- It is worth *suggesting* when a major feature or new plugin lands, after a significant rework, or before a release. A plugin that never gets regenerated never appears on the site at all — `textureSheet` and `threejs` were both missing from the published docs for exactly that reason.
- CI does not run it. `jsdoc` is a devDependency; the template has no others.
- Before a release: bump the version in both `package.json` and `src/engine.js` (`engineVersion`), run the build so `dist/` carries it, then the docs, name the changelog's Unreleased section for the version, and commit `dist/` and `docs/` with it: the release commit is the one that carries `dist/`. That, with screenshots, notes and the zip (`npm run build-release`), is for a minor or major release; a patch (1.24.1) is only the version bump, the changelog's section and `dist/` built and committed, for npm, with no zip and no docs. Also bump the `littlejsengine` range in `examples/vite-starter/package.json` and its lock on a minor or major release, so a project started from it gets the engine the docs describe.
- jsdoc exits non-zero on the TypeScript-flavored JSDoc used across the engine (tuples like `[Vector2, Vector2, number]` and arrays of them, records with optional fields like `{color?: Color}`, predicates like `a is Array<any>`, a function type grouped to join a union like `(function(number): Matrix4)|undefined`) which it cannot parse but which `dist/littlejs.d.ts` needs for precise types. The script verifies the generated output instead of the exit code — don't "fix" those JSDoc types to silence the errors. No spelling satisfies both tools: what jsdoc accepts in place of a tuple (`Array<Vector2|number>`, or a record type) throws the positions away, and a type predicate has no jsdoc-legal form at all.
- `checkJSDocMessages` in [tools/buildDocs.mjs](tools/buildDocs.mjs) counts those expected errors into one line and **fails the build on any other jsdoc message**, so a real tag problem cannot hide among them. If a new message is deliberate, widen the check there rather than letting the build print it on every run.

### Debug features
- Press `Esc` to toggle debug overlay
- Number keys toggle visualizations; `9` shows the tweakables panel and `0` opens the level editor, the 3D one when the game loaded a 3D level, after which `Esc` switches between playing and editing until the editor's Exit. A debug plugin adds a line to the overlay's key list through `debugOverlayKeys`
- `C` on the debug overlay is the free camera of a 3D game: the mouse looks, WASD and QE fly, the game runs on under it and reads no keyboard or mouse (`inputCapture`)
- `+`/`-` keys control time scale
- Debug functions: `debugRect()`, `debugCircle()`, `debugLine()`, `debugText()`, and in 3D `debugBox3D()`, `debugSphere3D()`, `debugLine3D()`, `debugPoint3D()`
